# W02 source and catalogue implementation

Implemented against accepted foundation `027327a` on 14 November 2026,
including `2bc3d5c`'s configured ingestion limits.
Specification 3.2.0 and contract 1.0 remain unchanged. No shared migration,
dependency, generated binding or application-composition edits are required.
Product milestones remain subject to the parent's integrated journeys.

## Parent composition

```python
from proscenium.catalogue import install, router, projects_router

catalogue = install(services)
app = create_app(services.settings, services=services,
                 routers=[projects_router, router])
```

`install(services: Services, *, limits: ImageLimits | None = None) -> Catalogue`
registers `artifacts`, `sources`, `catalogue` and `projects` in
`services.extensions`. Repeating installation returns the existing implementation.
The normal default reads `Settings.upload_max_bytes` and `upload_max_pixels`.
An explicit `ImageLimits` is a trusted host override, not a request option.
W01 remains responsible for the shared configured attachment count/total-byte limits
when admitting a message. W02 does not invent a second message-admission boundary.

The exported routers implement all 17 W02 operation IDs from
`docs/contracts/operation-owners.json`, including distinct GET and HEAD media
operations. Synchronous activation, rebind and settings commands return 200.
Create/open, upload, artefact registration and publication return 201 initially,
then 200 on matching replay. Opening creates no native session or job.

### Required W01 admission association

Tool callers require the active project, explicit operation allowlist, current
owner epoch, work ID and **original invocation ID**. The project-store
`invocations[caller.invocation_id]` record must contain:

```json
{"work_id": "original-work", "owner_epoch": "admitted-owner-epoch", "state": "running"}
```

`state: "admitted"` is also accepted. The associated `WorkRecord` must be
`running` or `awaiting_user` for a new effect, and the execution gate must be open.
W01 may retain additional private invocation fields. Operation replay binds the
original invocation and work before checking their current state. Completed
operations therefore remain readable after work finishes or execution closes.
Stale capabilities still fail the owner-epoch fence.

Allowlist operation names are `checkpoint_sources`, `publishOutputs` and
`registerToolArtifact`. W01 must retain the original invocation on an ACK-loss
retry, not create a replacement callback identity. Future request admission reads
`projects.settings()` to freeze the owner's private budget/profile settings.
`default_profile_id` must name a configured `project_scoped` profile from
`Settings.profiles`, not a renderer execution-profile ID.

### W03 transaction and read-model association

Publication uses `Jobs.create` and `Jobs.emit` within the publication transaction.
It queues `preview.render` using the F00 attempt identity. Each intent's body is
the existing F00 `{job_id, attempt_id, input_digest}`. No worker starts in W02.
The job target pins the exact item/version and optional shot, never the UI context.
Initial render specifications and all descriptive, provenance, Unity and ancestry
metadata remain in the immutable `versions` record.

`preview_intents[intent_id]` contains `{version, render_spec, job_id}`. W03's later
`request_preview` must use this same namespace for intent uniqueness. The trusted
`services.jobs.freeze_inputs(tx, job_id, inputs)` stores `{source, configuration, work_id, invocation_id,
owner_epoch}` for initial previews. `JobRecord.render_spec` holds the exact recipe.
The input digest fingerprints `{version, render_spec}` with RFC 8785.

W03 can promote completed bytes **before** its frame/segment transaction with
`artifacts.promote`, then call `artifacts.put(tx, artifact)` inside that same
receipt/job/event transaction. `promote` performs filesystem work only and does
not register a ready record. `metadata` may supply only `fps`, `frame_count`,
`dimensions` and `source_version_id`, and cannot replace hashes or identities.
Worker receipt paths must first be checked against W03's admitted output root.
They must not be sent through the generic tool-staging registration route.

Version reads derive later preview-job and artefact associations from render jobs
whose `target.version` is that exact version. Optional
`version_links[version_id] = {"artifact_ids": [...]}` supports additional trusted
links without rewriting the publication. Proxy reads require exactly one linked
mapping and validate its project, version, closure and proxy association. Multiple
ambiguous mappings fail rather than choosing an arbitrary sample.

### W05 selection association

W05 alone writes current typed `SelectionRecord` values in `selections`.
W02 derives item `selected_version_id` at read time. W05 need not modify W02's
`items` records. Storyboard `owner_selected` requires the exact
storyboard-version/shot/frame slot and a choice resolving to the authored frame's
current artefact. An authored `state: "selected"` is not owner authority.
A new plan version does not inherit the previous version's slot.
Sequence entry `choice: "owner"` is likewise derived from the exact assembly slot
and selected version, not trusted from authored JSON.

Authored shot plans validate referenced images, brief artefacts and version pins.
Sequence reads/publication validate the complete destination partition, admitted
source-job/version/shot/range associations, explicit retiming, ready frame-map
artefacts, complete map rows, reduced weights summing to one and declared
contributor intervals. Logical authored version references must also appear in
the source closure's dependencies. A source publication does not claim that
pending source-render frames are already available for assembly.

Canonical mask registration enforces untagged single-channel 8-bit PNG, without
alpha, transparency, EXIF orientation or colour/gamma reinterpretation.
`validate_mask` adds exact target dimensions and binary-versus-soft semantics.
W05 should call it at annotation/message admission, where the target is known.

## Source durability and scope

- Checkpoints use a project-local exclusive writer lock and a temporary Git
  index based on the expected parent. They do not update the owner's index.
- Before creating Git objects, a FULL-synchronous SQLite intent freezes the
  request/invocation fingerprint, branch, expected parent, owned byte hashes,
  executable modes and commit identity/date.
- Commit trailers carry the operation ID and fingerprint. One Git ref
  transaction CAS-updates the branch and creates
  `refs/proscenium/checkpoints/<sha256(operation_id)>`.
- Reconciliation validates the checkpoint ref, parent, exact prepared tree,
  trailers and hydrated owned hashes. HEAD may have advanced. The original
  source commit is returned without creating another commit.
- If a ref effect cannot be proved, the receipt is `outcome_uncertain` with a
  null source commit. That operation stays fenced while its exact checkpoint
  ref is absent. A late verifiable ref completes it on retry. There is no
  automatic destructive repair or fresh commit for an unresolved operation.
- Contract 1.0 checkpoint paths identify extant files. A deleted file has no
  representation in `CheckpointReceipt.files`; this implementation does not
  invent a deletion/hash convention.
- Source closure digests exclude `digest`, use RFC 8785, sort file destinations
  and dependency item/version IDs, and verify hydrated local Git LFS objects.
  Missing LFS content never triggers a network fetch.
- Closures reject cross-project repositories, unsafe/secret/runtime paths,
  symlinks, conflicting destinations, absent entry files and missing version
  dependencies. Publication validates the entire dependency/ancestry DAG and
  all expected heads before committing any item.
- Snapshots contain copies, not links to live authoring or retained files.
  Files are read-only and the populated tree has a sealed, rehashed receipt.
  Retained source registration requires an explicit owner's keep-out-of-Git
  reason. Licence metadata never supplies that decision.

## Native inspection boundary

Ordinary project/catalogue reads and `materialise()` do not launch Blender.
W03 must verify native dependencies before admitting its renderer to the source:

```python
from proscenium.sources.inspection import (
    BlenderInspectionAllocation, inspect_blender,
)

report = inspect_blender(
    services, project_id, materialised_root,
    BlenderInspectionAllocation(allocation_id, installed_blender, threads=4, timeout=180),
    expected_digest=version["source"]["digest"],
)
```

This trusted allocation is not model-supplied JSON. The fixed entry point uses
factory startup, disabled auto-execution, at most four CPU threads and a maximum
180-second process timeout. It validates the receipt and exact Blender version,
rehashes before/after, opens the actual `.blend`, and rejects undeclared, missing
or escaped paths reported by Blender's external dependency traversal. W03 still
owns render-engine/device/feature admission, dynamic frame/cache requirements,
resource claims and actual rendering. Static reopening is not render acceptance.

## Project stores, media and recovery

Workspace bootstrap follows the normative directories, Git/LFS installation,
ignore list and attributes. A nested repository directory is rejected. Project
identity is retained in `project_identity["identity"]`. Registry/settings remain
machine-private. Rebind validates a settled matching project database, ready
artefacts, retained bytes, source commits and hydrated LFS objects. A copied
database must equal the still-present settled original. Native session relocation
requires the parent's trusted `native_rebind_verifier(project_id, new_root,
native_session_id)` extension and otherwise fails `native_session_missing`.

Registry activation and its project event cannot share one SQLite transaction
under F00's separate-store contract. W02 uses a durable machine
`project_commands` record and idempotent project-event reconciliation instead.
A retry repairs a missing event without incrementing the revision again.
Publication, versions, heads, initial jobs, intents and events **do** share one
project SQLite transaction. Settings updates are private registry transactions.

Additional collections use F00's existing `records` table, not new physical
tables or migration revisions:

| Store | Namespace | Key |
| --- | --- | --- |
| Machine | `project_open_intents` | Original open operation ID and fingerprint. |
| Machine | `project_commands` | Original activation operation ID and event recovery record. |
| Project | `project_identity` | `identity`, stable project/repository IDs. |
| Project | `checkpoint_intents` | Checkpoint operation ID. |
| Project | `retained_sources` | Explicitly retained source artefact ID. |
| Project | `publications` | Publication ID and original admission association. |
| Project | `preview_intents` | Render intent ID shared with W03. |
| Project | `version_links` | Optional derived links keyed by immutable version ID. |

F00's `operations` journal remains authoritative. The small W02 `replay` helper
only reads that existing table with F00's canonical fingerprint semantics.
A future shared `Transaction.lookup_operation(scope, identity, body) -> dict | None`
would remove that direct read without introducing another operation journal.

The parent should coordinate all other packages' owner mutations with
`Services.activation_lock` during copy/rebind, so a concurrent selection/request
cannot modify the old database after the settled-copy equality check. W02's own
lifecycle operations already use that shared lock. This is a shared integration
guard, not permission to change F00 from this package.

Uploads preserve the original bytes. EXIF/ICC and non-display colour-mode
conversion produce an explicitly linked PNG display derivative. Trusted worker
promotion preserves supplied bytes and transformations exactly. Tool registration
accepts only `.proscenium/tool-output/staging/...`, not arbitrary project paths.
The parent must ensure tool-produced display images already declare the required
orientation/colour transformations when using exact-byte promotion.

Media IDs resolve only immutable managed hash paths. GET/HEAD rehash the byte
buffer actually served, support one normal/open/suffix byte range, return exact
206/416 headers, and use authenticated private immutable caching, hash ETags,
`nosniff` and a restrictive content security policy. No raw-path route exists.

Project snapshots read complete held `RequestRecord` values, active `WorkRecord`,
items, jobs, pending decisions and review tickets in one project transaction with
its event watermark. Empty feature collections are valid.
