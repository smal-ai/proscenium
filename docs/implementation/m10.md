## Blocker 1: a late W03 mapping cannot validate a picked-object Queue

Actual browser `POST /api/v1/projects/<project>/contexts` returned HTTP **409 `source_conflict`**
with the real picked pair. No request or cloud root was admitted. A second explicit reproduction
captured the same definitive rejection before any model request.

`copilot/context.py:Contexts.validate_references` reads only the stored immutable
`version["artifact_ids"]` when validating selected objects. The imported source publication
contains four original source/image/provenance artefacts. W03 later adds the actual proxy and
mapping through `version_links`, as designed. W02's public version read model correctly exposes
all six. W01 finds no nodes because it ignores those later associations.

The isolated diagnostic proves the same valid mapping is accepted when initially attached to
the raw version and rejected when it is present only through the supported late-link seam.

**Parent fix required:** resolve authoritative, correctly pinned W02/W03 proxy-map associations
inside context validation. Do not rewrite the immutable version, fabricate a mapping or weaken
object/project/source-closure checks.

To continue independent M10 work, the scripted test user explicitly Control-clicked the actual
outliner node to deselect it. A new context with the same precise version and empty object list
was then admitted. This is a disclosed **version-only fallback**, not a pass of selected-object
context hand-off. The original pre-admission rejections and screenshot remain retained.

## Blocker 2: identical shell payload, distinct native permission IDs

The admitted native root prepared its own script and requested the bounded, four-thread,
OS-claimed Blender command. The SDK emitted two `permission.requested` events for that same
tool call and identical `permissionRequest` JSON, first for a path prompt, then commands.
Their native request IDs differ. The first was approved by routine host policy.

`copilot/state.py:State.reduce` keys a permission binding using `(tool_call_id,
SHA256(canonical(permissionRequest)))`, but includes the native request ID in its immutable
binding. The second valid stage reuses that key with a different native ID. `State.bind`
rejects it as **`attribution_unavailable`**. The host fences the project and rejects execution.

The runtime labels the second completion `denied-interactively-by-user`. This was **not** a
human decision. The host correlation failure caused it. No authoring Blender process started.

**Parent fix required:** preserve distinct native permission request identities/stages and
their original work/invocation/epoch attribution, including repeated identical payloads.
The SDK callback omits its request ID, so a safe pending-event correlation strategy is needed.
Do not overwrite immutable bindings, fabricate user approval or bypass the callback in a script.
