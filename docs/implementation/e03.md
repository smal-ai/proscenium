# E03: bounded progressive-media feasibility

**Result:** the small native render-to-independent-segment path works. This does not close product rendering, uninterrupted playback or M08 acceptance.

**Run:** 14 November 2026, 13:12 SAST. Accepted base `148ad0fee19de17317fba46aece4b1c18f006ab5`, specification 3.2.0 and contract 1.0.0. [Recorded measurements and hashes](../evidence/e03/measurement.json).

- Exactly one Blender process rendered 12 frames. Cycles CPU, four render threads, eight samples, 640 × 360, 24/1 FPS, denoising off, seed 0. No display, GPU or model service was used.
- Blender 4.5.14 LTS build `62c1db4208e8`, FFmpeg/ffprobe `8.0.1-3ubuntu2`, Python 3.12.13, Pillow 12.3.0 and Playwright 1.65.1.
- The worker kept `camera: null`. Recorded camera matrices and moving-cube positions change between frames 1 and 12. The scene's authored camera was not replaced.
- PNG output is RGB, 8-bit, with Blender's Standard view transform baked by `render(write_still=True)`. Display device sRGB, look None, exposure 0, gamma 1. No source save occurs.
- The first segment encoded entirely inside frame 5's render interval. Frame 12 did not exist when the segment became ready. Both the filesystem observation and monotonic timestamps are retained. No sleeps or artificial throttling were used.
- Source closure was copied into disposable storage, files made read-only, and original/copy hashes checked after rendering. Inputs are the historical linked-v1 asset/texture fixture, not the current v2 working tree.
- The OS-held `blender-render.lock` covered Blender's process lifetime. Timeout handlers terminate only their own process groups. Render bound 300 s, each encode bound 60 s, one encoder at a time.
- Blender's internal memory log reported a peak of `27.13M`. This is **not OS RSS**. CPU utilisation, RSS and GPU telemetry were not measured. The source closure is 859,890 bytes. Native PNGs total 4,121,266 bytes. This tiny scene is not a representative production benchmark.

Four frames is a functioning **proof interval**, not a universal segment-size decision. It gives 1/6 s at 24/1 and 1001/6000 s at 24000/1001. Native first-playable accumulation cost dominates the measured encoder overhead. W03/W05 should retain this small interval for regression fixtures, then measure practical segment length and buffering against real scenes and their accepted player.

- The CSS viewport was 1920 × 1080. Video was letterboxed inside 960 × 640 CSS pixels, with 960 × 540 content. Canvas captured intrinsic video pixels. This is not a product pointer-coordinate test.

## Consumer hand-off

**W03**

- Consume W02's accepted materialisation service and F00's jobs/claims/events when product work becomes ready. These scripts intentionally have no production imports, database records, authentication or competing schema.
- Use a fixed worker entry point with validated job data. Keep authored cameras when the override is null and do not save render settings into sources.
- Publish each complete frame plus verified immutable receipt first. Encode only contiguous receipted intervals. A single encoder thread overlaps later rendering here without delaying the worker.
- Preserve source ordinals, exact rational rates, input PNG hashes and distinct encoded hashes. MP4 PTS restart at zero for every independent segment. Segment interval metadata, not media time alone, identifies the source frame.
- Do not infer completion from a high frame number. This sequential fixture cannot substitute for product hole/failure/recovery/cancellation tests.

**W05**

- Use `f03/fixture.json` and `f04/fixture.json` as actual media inputs. Convert the proof-specific receipt metadata to the accepted product contract at the test boundary. Do not copy it as a new shared DTO.
- For source frame `f` in segment starting `s`, request centre `(f-s+1/2) × denominator/numerator`. Confirm the actual presented frame with rVFC/capture before pinning annotation identity. Local PTS resets in each segment.
- Withhold availability of interval 5–8 while exposing 1–4 and 9–12 in the product fixture. Stop/buffer at the hole, then check ordered resume and that paused annotations remain paused. E03 supplies the bytes, not this behaviour.
- Run continuous product playback in all three actual browsers. Observe every ordinal once, especially `4→5` and `8→9`, with blank/duplicate/skip and drift detection. Paused stepping is not that acceptance test.
- Standalone MP4 compatibility does not prove that these files work as MSE append buffers. A prebuffered independent-segment player is compatible with the measured format. Any MSE packaging or adapter needs its own proof.
- Repeat real pointer-coordinate/annotation restoration at DPR 1/2 and letterboxing, plus final-assembly lineage. These remain unproven here.
